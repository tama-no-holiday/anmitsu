# anmitsu 1.0.0 ソースの検証結果

対象: 書き出したソース（元のコミット `0283d4e`、versionName 1.0.0・versionCode 1、パッケージ名 `io.github.tama_no_holiday.anmitsu`）。どれも開発者の環境で実行したもので、ツールは既存のものを使っています。

**まとめ:** 検証は2回あり、条件が違います。辞書・AIを入れた検証（A）では、debug・release の `:app` テストがそれぞれ1件失敗し、原因は未解決です。辞書・AIを入れない fixture 限定の検証（B）は全タスクが成功しました。B の成功は A の失敗が解決したことを意味しません。すべてのテストが合格したとは言えません。

## A. 辞書・AIを入れた検証（以前の記録）

既存のツール・キャッシュと、既存の辞書・AIのファイルを使って、最初の書き出しの複製で実行しました。

### A.1 テスト

| 対象 | 結果 |
|---|---|
| Python（`python -m unittest discover tests`） | 56件合格 |
| `:core:test` | 118件合格 |
| `:oss-converter:test` | 105件合格 |
| `:app:testDebugUnitTest` | 521件中 519件合格・**1件失敗**・1件スキップ |
| `:app:testReleaseUnitTest` | 521件中 519件合格・**1件失敗**・1件スキップ |

失敗したテスト（どちらも `InputUiTest`、debug と release で別のテスト）:

- debug: `backspaceHonoursACaretTappedInsideTheSelectedSegment`（1103行）。期待 `[あしは|, 雨]`、実際 `[明日|, 雨]`。このテストだけを実行し直すと合格しました（1件中1件）。
- release: `backspaceOnTheFirstSegmentDeletesItsLastKanaThenContinuesBackwards`（1013行）。期待 `[あし|, 、, 雨]`、実際 `[朝|, 、, 雨]`。実行し直していません。

**未解決。** 原因は確かめていません。テストのコードを読んで分かったのは次の2点だけです。

- 待ち合わせの補助関数 `pumpUntil` は、条件がそろわないまま 300回×10ms が過ぎても失敗せずに戻ります。
- 1013行のテストのコメントには「あし: no word」とありますが、別のテストは、試験用の辞書が「あし」を「朝」に直すことを前提にしています。

どちらも、テストの期待値か待ち方の問題を疑わせますが、根拠にはなりません。利用者に見える不具合かどうかも確かめていません。アプリとテストは変えていません。

### A.2 ビルド・lint・パッケージ化

- テストの失敗のあとも `--continue` で `assembleRelease` と `lintRelease` を実行し、両方のタスクが完了しました。Gradle 全体の終了コードは、テストの失敗のため 1 です。
- lint: エラー 0、警告 3（`NewerVersionAvailable`、`UnsafeDynamicallyLoadedCode`、`ClickableViewAccessibility`）。
- `scripts/package-android.ps1 -Version 1.0.0 -Release -RequireOss -RequireZenz`: 終了コード 0。できたのは**署名していない**APKです（SHA-256 `da7457e1ab2dc91965a7569ce14a6c5f3806b39eafa910536843fded0ae8e2da`）。公式APK（`2f454398…`、署名済み）とは別のファイルです。公式APKは変えていません。

### A.3 公式APKとの比較

`META-INF/` を除くすべての項目を比べました。

- 37項目はバイト単位で同じ（dex、リソース、辞書、モデル、ネイティブライブラリを含む）。
- 4項目は改行（CRLF と LF）だけが違う: `assets/lexicon.tsv`、`assets/licenses/Kotlin-LICENSE.txt`、`assets/licenses/Kotlin-NOTICE.txt`、`assets/licenses/THIRD-PARTY.md`。
- 片方にしかない項目はない。

**これはビルドの再現性の証明ではありません。** ネイティブライブラリ（`libastra_zenz.so`）は新しくビルドせず、公式APKから取り出してロックのハッシュと照合したものを使いました。ツール・キャッシュ・辞書・モデルは開発者の環境にあったもので、何もない環境から取得し直してはいません。

`scripts/ci-baseline.ps1` をローカルで実行しました（[docs/ci-baseline.md](../ci-baseline.md)）。辞書・AIのファイルは渡さず、テストは小さな試験用の辞書で動きます。ツールは既存のものを再利用しました。

この検証の範囲:

- 辞書・AIを入れた構成、`assembleRelease`、release のテスト、公式の署名は含みません。リリース品質の確認ではありません。
- 何もない環境（GitHub Actions の新しいランナーなど）でツールを取得するところからの実行は、まだしていません。
- B で実行したのは debug のテストだけです。A の debug の失敗は B では再び起きませんでした。A の release の失敗は、release のテストを実行していないため、B では確かめていません。
- A の2件の失敗は、どちらも原因が分かっていません。解決済みとは扱いません。

## C. 書き出しとソースの対応

- 2026-11-22 の確認で、最初の書き出し（ソースの259ファイルと `SOURCE-MANIFEST.txt` の、合わせて260ファイル）について、259ファイルのハッシュは `SOURCE-MANIFEST.txt` の記録とすべて一致しました。秘密鍵・APK・GGUF・`.so` のファイルは入っていません。トークンらしい文字列の限られた検査でも該当はありませんでした。これは秘密の情報が入っていないことの完全な保証ではありません。
- **`SOURCE-MANIFEST.txt` は最初の書き出しの記録です。** その後に加えた・直したファイル（CIベースライン、`LICENSE`、README などの文書、`.github/` のテンプレート）は反映していません。後から変えたファイルのハッシュが記録と違うのは想定どおりです。アプリのコード・版・同梱するファイルは書き出しのときのままです。

- R8（無効のまま）、ビルドの再現性
- 変換の精度は開発用の例で測ったもので、一般の文章での精度を示すものではありません。
- 開発者本人が公式版をしばらく使い、目立った問題はなかったと報告しています（2026-11-21。期間・端末・OSの版は記録していません）。これは感想で、検証ではありません。
