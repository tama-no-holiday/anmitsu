# 評価資産

このディレクトリはPoC用に作成した合成・手作成データだけを含む。実ユーザーの入力、入力履歴、実測タッチ軌跡は含まない。`lexicon.json`は小規模な開発用辞書であり、実用辞書の代替ではない。

`evaluation.jsonl`の代表文は依頼者提供の開発例。それ以外は今回作成した短文。外部コーパスを転載していない。ここでの試験は一般日本語での精度や権利が確認された外部学習データの利用を証明しない。

- `development`: 調整に利用できる既知例。代表文はここに含める。
- `compositional`: 既知語彙を組み合わせた文単位の試験。実装者にも語彙・一部の文型が見えているため、真のブラインドholdoutではない。
- `clean`: 正しい読み。通常の漢字化を過剰補正と数えず、Top-1の読みが変わったかを測る。
- `oov`: 未登録固有名詞・口調・文字種。原文候補保持とTop-1の改変を別に数える。
- `synthetic_touch`: 手作成の曖昧な観測仮説。正解を100%にするoracleではなく、誤った方向を支持する行も含む。座標列から測った分布ではない。

`input`が唯一の本文入力、`reading`は評価用正解、`surfaces`は許容表記。正解は評価器だけが読む。エンジンはこのファイルを読まない。タッチ仮説のindexは観測文字列のUnicodeコードポイント位置で、挿入・削除時にも意図文字のindexと混同しない。

次段階では語彙外の凍結文、独立したユーザー、同意を得た実測軌跡、編集種別・誤り数・文長・専門領域を層別した数百〜数千例を追加する。今回の小規模試験を学習/開発/テストの完全分離済みとは主張しない。

## Android試験運用の回帰データ

`feedback-regression.jsonl` は依頼者が明示した「ありがとう」の不適切な補正と、Astraが作成した日常文・架空の未知語・近い誤入力の合成25件。実ユーザーの入力履歴から採取したものではない。元の25件と併せた50件を `scripts/export-feedback-cases.ps1` でKotlinテスト用TSVへ変換する。エンジンは正解・評価データを読み込まない。

修正前を `reports/feedback-before-0.1.0.json` に記録した。このデータを見て語彙と保守的な補正方針を改善しているため、修正後も開発評価であって未知文の性能ではない。`kind=clean/unknown` のTop-1読み改変、Top-1表記一致、候補内正解、禁止候補の有無を別に評価する。手作成語彙を増やした効果と、未知語を修正しない効果を混同しない。

修正後は `reports/feedback-after-0.1.1.json`。このホスト評価の `recall10` は最終表記候補10件内の一致であり、読み候補生成のRecall@Kではない。`reading_changed` は評価用正解読みとの不一致なので、誤入力例では未補正もtrueになる。過剰補正として集約するのはclean/unknownの22件だけ。各例1回の事前実行と10回の測定によるp50/p95は参考値で、実機性能・安定した裾遅延を示さない。

`dictionary-probes.tsv` は辞書拡張（Mozc-UT取り込み、`docs/dictionary-update.md`）の新旧比較用に Claude が作成した33例（`ossCli compare` / `demo` 形式: id, category, typed, reading, 許容表記`|`区切り）。`common` は一般日本語の回帰確認（新辞書で悪化してはならない）。`name-dev`/`english-dev`/`new-word-dev` は人名・英語表記・新語の開発例で、許容表記は公開辞書に載っていそうな一般的表記を手で選んだもの。どの UT 辞書に実際に含まれるかは確認しておらず、ブラインド評価でもない。未知語のカタカナ候補は辞書ではなくアプリ側（`LiteralChoices`）で保証するため、ここでは測らない。

`context-eval.tsv` は確定済みの前文を使う変換（0.1.28）の評価用合成30例（`ossCli context-eval` 形式: id, group, 読み, 許容表記`|`区切り, 前文）。`request` は依頼者提供の2例。`homophone` は実モデルの結果を見る前に Claude が作成した同音語の例。`control` は無関係な前文で、前文なしからの順位変化を測る。可視の開発例であり未知文の性能は示さない。結果を見て例や重みを調整しない。実ユーザーの入力は含まない。

`context-holdout/` は文脈の順位付け方式を判定する合成データ（`ossCli context-policy-eval` 形式: id, 読みの系統, 種別, 読み, 許容表記`|`区切り, 前文）。例と許容表記はすべて Claude が作成し、モデルも変換器も実行する前に `manifest.json` へハッシュを記録した。読みの系統のハッシュで dev と holdout に分け、`context-eval.tsv` とは系統も表記も重ならない。holdout は採否の判定だけに使い、調整には使わない。独立した人手のラベルではなく、実ユーザーの試験でもない。手順は `context-holdout/protocol.md`。ハッシュはこの作業ツリーのLF改行のファイルのもの。

`oss-conversion-regression.jsonl` はOSS統合時に新設した合成20例（正しい読み15、架空未知語3、混在文字2）。OSS実行結果を見る前に作成したが、以後は可視の開発回帰例でありブラインド評価とはしない。通常変換の語彙を確認するセットで、誤入力復元の精度とは区別する。正解表記の手調整で成績を上げず、許容表記を変更した場合は理由を記録する。
